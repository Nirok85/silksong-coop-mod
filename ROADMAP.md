**Актуально на:** v2.2.0 (687/687 тестов, 0 ошибок, 0 предупреждений; Mod собран против реальных сборок игры)

- **Надёжность/тесты.** 687 тестов, регрессионные наборы на сетевой слой, смерть/возрождение, packet validation, max-stats, врагов и дропы.

## 🔴 Приоритет 1 — Архитектура и надёжность (спринты 1–2)

### 1. Декомпозиция god-объекта `SilksongCoopPlugin` (1497 строк)
**Проблема:** класс смешивает транспортную оркестрацию, обработку пакетов, revive-логику, применение предметов, рассылку трансформаций и Unity lifecycle.
**Действие:**
- Извлечь `NetworkOrchestrator` (выбор транспорта, connect/disconnect, polling).
- Извлечь `PacketDispatcher` (роутинг входящих пакетов по типам).
- Извлечь `GameplaySyncController` (revive, team wipe, применение предметов и vitals).
- Извлечь `TransformReplicationService` (тик-рассылка трансформаций).
- Оставить `SilksongCoopPlugin` тонкой точкой входа BepInEx (<200 строк).
**Критерий приёмки:** каждый сервис < 350 строк; все 614 тестов проходят; поведение идентично.

### 2. Разделение `CoopMenuUI` (1253 строки) на компоненты
**Проблема:** один класс рисует окно, 4 вкладки, тосты, HUD напарника, историю подключений.
**Действие:**
- Извлечь `Tabs/HostTab.cs`, `Tabs/JoinTab.cs`, `Tabs/StatusTab.cs`, `Tabs/SettingsTab.cs` (~200 строк каждая).
- Извлечь `UIComponents/PartnerVitalsHud.cs` и `UIComponents/WatermarkRenderer.cs`.
- Ввести общий интерфейс `IMenuTab { void Draw(); }` и список вкладок в `CoopMenuUI`.
**Критерий приёмки:** ни один UI-файл не превышает 350 строк; визуально ничего не изменилось.

### 3. Устранение синглтона `SilksongCoopPlugin.Instance` (DI-подход)
**Проблема:** статический синглтон доступен из ~40 мест, скрытые зависимости, тесты завязаны на глобальное состояние.
**Действие:**
- Ввести lightweight-контейнер: `CoopServices` с явной регистрацией сервисов при инициализации.
- Core-сервисы получают зависимости через конструкторы (уже частично так).
- Mod-компоненты получают зависимости в `Initialize()`, а не через `Instance`.
**Критерий приёмки:** `Instance` остаётся только для BepInEx-логирования; все сервисы тестируются изолированно.

### 4. Единый `ILogger`-абстракция в Core
**Проблема:** Core использует `System.Diagnostics.Debug.WriteLine` (не виден в проде), Mod — `SilksongCoopPlugin.LogWarn`. Два разных мира логирования.
**Действие:**
- Создать `SilksongCoop.Core.Diagnostics.ILogger` + `NullLogger` (по умолчанию).
- Mod-слой регистрирует `BepInExLogger`-адаптер при старте плагина.
- Заменить все `Debug.WriteLine` и локальные `Log()`-хелперы на `ILogger`.
**Критерий приёмки:** все логи мода видны в `LogOutput.log`; Core не зависит от Mod.

### 5. Потокобезопасность транспорта: аудит и стресс-испытание
**Проблема:** `LiteNetLibTransport.PollEvents()` вызывается из основного потока, но события отписываются в очередь `FirePendingEvents` — гонки возможны при мультипирном будущем.
**Действие:**
- Написать многопоточный стресс-тест (N потоков шлют `Send`, основной поток поллит).
- Заменить `lock (_lock)` + `Queue<Action>` на `ConcurrentQueue<Action>` с ID-паттерном.
- Добавить `CancellationToken` в `PollEvents` для graceful shutdown.
**Критерий приёмки:** 10-минутный стресс-тест без исключений и дедлоков.

## 🟠 Приоритет 2 — Геймплей и сетевой код (спринты 3–4)

### 6. Предикция и компенсация задержки для локального игрока
**Проблема:** локальный игрок «идеален», но видит напарника с задержкой 50+ мс (TargetDelayMs) — в бою это заметно.
**Действие:**
- Уменьшить `TargetDelayMs` адаптивно по jitter (50 → 20 мс при стабильной сети).
- Добавить клиентскую предикцию для врагов, которых бьёт удалённый игрок (reconciliation).
**Критерий приёмки:** hit-регистрация slash-атаки удалённого игрока совпадает с визуальным положением клона в ≥95% случаев.

### 7. Синхронизация сцен и переходов между комнатами
**Проблема:** пакет `SceneTransitionPacket` добавлен, но переходы обеих сторон не атомарны — возможен «двойной переход» или рассинхрон чекпоинтов.
**Действие:**
- Реализовать 3-фазный протокол: запрос перехода → подтверждение → одновременная загрузка.
- Синхронизировать `BenchCheckpointSyncPacket` с той же логикой.
**Критерий приёмки:** 100 последовательных переходов в тестовом сценарии без рассинхронов.

### 8. Восстановление после разрыва: rollback мира
**Проблема:** при reconnect клон пересоздаётся «с нуля» — состояние врагов, открытых дверей и событий мира не сверяется.
**Действие:**
- Периодическая (раз в 10 с) рассылка «world digest» — хэш ключевого состояния.
- При расхождении хэшей — ресинк по списку открытых предметов/событий.
**Критерий приёмки:** принудительный disconnect на 30 с → reconnect → мир идентичен.

### 9. Поддержка 3+ игроков (мультипирная архитектура)
**Проблема:** вся сеть построена вокруг 1:1 (один удалённый клон, один endpoint).
**Действие:**
- Модифицировать `INetworkTransport` на мультипирную модель (`IEnumerable<NetworkPeerId>`).
- Steam: лобби уже мультипирное; UDP: mesh-топология или релей через хоста.
- `RemoteHornetSpawner` уже поддерживает словарь клонов — расширить UI статуса.
**Критерий приёмки:** 3 игрока в одной комнате видят и слышат друг друга (фаза исследования).

## 🟡 Приоритет 3 — UX и визуал (спринты 5–6)

### 10. Локализация UI (RU/EN/пользовательские)
**Проблема:** строки UI захардкожены частично на английском, частично на русском (тосты F11 — русские).
**Действие:**
- Создать `Localization/Strings.cs` со словарём `key → (en, ru)`.
- Выбирать язык по языку игры Steam (`Silksong.Language`), переопределять в конфиге.
- Все тосты, кнопки, подсказки — через систему локализации.
**Критерий приёмки:** ни одной захардкоженной строки в UI-классах.

### 11. Ин-гейм «руководство нового игрока» (onboarding)
**Проблема:** новые игроки не знают про F10, коды комнат и правила смерти.
**Действие:**
- При первом запуске (по конфигу `[Onboarding] ShowIntro = true`) показывать 3-шаговый туториал-оверлей.
- Кнопка «Show Help» в меню — открывает сокращённую версию.
**Критерий приёмки:** туториал показывается один раз, отключается в конфиге.

### 12. Красивый HUD напарника + индикация состояний
**Проблема:** vitals HUD есть, но нет индикации «напарник умер», «напарник в другой комнате», «напарник на скамейке».
**Действие:**
- Добавить status-иконки (мини-иконки рядом с портретом напарника).
- Пульсирующая обводка при низком HP напарника (<25%).
**Критерий приёмки:** все состояния напарника считываются с HUD без открытия меню.

## 🟢 Приоритет 4 — Инфраструктура и дистрибуция (спринты 7–8)

### 13. CI/CD: GitHub Actions
**Проблема:** релизы собираются вручную локально — риск «забыть пересобрать» или расхождения DLL.
**Действие:**
- Workflow `build.yml`: push/PR → build Debug+Release (warnings-as-errors), запуск 614 тестов.
- Workflow `release.yml`: тег `v*` → сборка, упаковка `final/`, создание GitHub Release с asset.
- Публикация артефактов сборки на каждый PR.
**Критерий приёмки:** релиз v2.2.0 собирается одной кнопкой «Run workflow».

### 14. Точка входа для мод-менеджеров (r2modman/Thunderstore/Gale)
**Проблема:** установка вручную — барьер для казуальных игроков.
**Действие:**
- Добавить `manifest.json` (Thunderstore формат): `name`, `version_number`, `dependencies: ["BepInExPack-5.4.21"]`.
- Публиковать релизы также на Thunderstore (Silksong community).
- README-секция «Установка через мод-менеджер».
**Критерий приёмки:** мод ставится через r2modman в 3 клика.

### 15. Перформанс-бюджет и профилирование
**Проблема:** нет измерений — неизвестно, сколько CPU/памяти ест репликация 30 Гц + интерполяция.
**Действие:**
- Добавить в DiagnosticsOverlay (F11) счётчики: время Update() мода за кадр, GC alloc/cadр, размер буферов.
- Бюджет: < 0.5 мс/кадр на репликацию, < 1 КБ alloc/кадр в steady-state.
- Бенчмарк-сценарий (2 клона + 50 врагов + боссфайт) с фиксацией метрик в тестах.
**Критерий приёмки:** диагностика показывает реальные числа; бюджет соблюдён; бенчмарк в CI.
