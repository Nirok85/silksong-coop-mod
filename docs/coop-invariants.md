# Инварианты кооперативной сессии

> **Исторический снимок протокола v8.** Не используйте как текущую нормативную
> спецификацию: формат сейчас v11. Актуальные правила — в
> [state-authority.md](state-authority.md) и [protocol-v11.md](protocol-v11.md).

Документ фиксирует правила, которые обязаны выполняться независимо от
транспорта (UDP или Steam), порядка пакетов и момента подключения. Изменение
поведения требует обновления этого файла и тестов, а не только кода.

Версия протокола в этом снимке: **v8**. Документ не вводит новых пакетов и полей.

## 1. Роли и авторитет

| ID | Инвариант | Где проверяется |
|---|---|---|
| AUTH-1 | Хост является авторитетным симулятором врагов, смерти и общего мира. | `EnemySyncService`, `EnemySyncController` |
| AUTH-2 | Клиент не может самостоятельно подтвердить смерть врага, которого хост ещё считает живым. | `EnemySyncRemediationTests`, `EnemySyncAuthorityTests` |
| AUTH-3 | Смерть от клиента — это заявка на урон. Хост объединяет её со своим HP; смерть принимается только при летальном суммарном уроне. | `EnemySyncService.TryAcceptRemoteHit(LocalHost)` |
| AUTH-4 | Пакет от авторитетного хоста заменяет абсолютный HP, а не вычитается из локального. Это исключает двойной учёт удара, уже вошедшего в snapshot. | `EnemySyncService.TryAcceptRemoteHit(Authoritative)` |
| AUTH-5 | Пока авторитет хоста свеж (TTL 3 с), пакеты других клиентов по этому врагу игнорируются. | `RemoteHitPolicy.Deferred`, `HasFreshHostAuthority` |
| AUTH-6 | Клиент не может отправить авторитетный snapshot: пакеты snapshot принимаются только от хоста. | `EnemySyncController.ApplyRemoteSnapshot` |
| AUTH-7 | Локальный игрок имеет право менять собственные vitals/инвентарь; удалённые значения проходят валидацию диапазонов. | `PacketValidator`, `VitalsSyncService` |

## 2. HP, урон и snapshot

| ID | Инвариант |
|---|---|
| HP-1 | HP врага монотонно не возрастает в пределах одного жизненного цикла, кроме явного respawn/нового экземпляра. |
| HP-2 | Повторный пакет с тем же или меньшим sequence от того же отправителя не применяется. Sequence `0` означает «без версии» и не дедуплицируется. |
| HP-3 | Snapshot с меньшим timestamp, чем уже применённый, отбрасывается. |
| HP-4 | Snapshot не воскрешает врага, отмеченного мёртвым. |
| HP-5 | Snapshot, снятый до последнего локального удара, не повышает HP. Он может понизить HP или подтвердить смерть. |
| HP-6 | Летальный удар, ожидающий подтверждения хоста, оставляет 1 HP и не помечает врага мёртвым. |
| HP-7 | Одновременные удары объединяются аддитивно только тогда, когда snapshot не мог содержать локальный удар. |
| HP-8 | Реестр врагов ограничен по размеру (1024) и вытесняет самые старые записи, не очищая весь реестр. |

## 3. Смерть и возрождение

| ID | Инвариант |
|---|---|
| DEATH-1 | Смерть и revive идемпотентны: повторный пакет не запускает эффект второй раз. |
| DEATH-2 | Удалённая смерть регистрируется в локальном жизненном цикле до отправки подтверждения. |
| DEATH-3 | Revive выполняется только по подтверждённому триггеру напарника и с проверкой безопасной точки. |
| DEATH-4 | После respawn состояние HP/позиции синхронизируется, а устаревшие пакеты прошлой жизни не применяются. |
| DEATH-5 | Team wipe и spectator-режим не отправляют transform/боевые события как живой игрок. |

## 4. Сохранения и replay

| ID | Инвариант |
|---|---|
| SAVE-1 | Replay-регистры (мёртвые враги, world events, persistent state) привязаны к текущему сохранению. |
| SAVE-2 | Reconnect внутри одного прохождения сохраняет replay-регистры. |
| SAVE-3 | Смена слота или перезагрузка сохранения очищает replay-регистры до отправки новому партнёру. |
| SAVE-4 | Profile id `0` (меню) не считается сменой сохранения. |
| SAVE-5 | Переход `PlayerData` из `null` в объект не является сменой сохранения; сменой считается другой non-null объект или другой profile id. |
| SAVE-6 | Persistent-состояние, пришедшее для незагруженной сцены, не применяется к чужой сцене и повторяется после загрузки. |
| SAVE-7 | Пустой snapshot quest-флагов не затирает локальные значения. |

## 5. Reconnect и late join

| ID | Инвариант |
|---|---|
| JOIN-1 | Новый peer получает полный catch-up: сцена, checkpoint, vitals, инвентарь, мёртвые враги, world/persistent state. |
| JOIN-2 | Catch-up идемпотентен и не создаёт дублей. |
| JOIN-3 | Пакеты, полученные до готовности peer, либо ставятся в ограниченную очередь, либо отбрасываются по явному правилу; неограниченного роста нет. |
| JOIN-4 | Смена сцены одним игроком не применяет события другой сцены к локальным объектам. |
| JOIN-5 | Reconnect не переиспользует identity незавершённого handshake другого endpoint. |
| JOIN-6 | После завершения сессии события старой сессии не доставляются в новую. |

## 6. Транспорт и безопасность

| ID | Инвариант |
|---|---|
| NET-1 | Handshake проверяет версию протокола и HMAC; несовпадение версии отклоняется. |
| NET-2 | MAC проверяется до расхода токена rate-limit, чтобы невалидный трафик не мог исчерпать бюджет честного peer. |
| NET-3 | Rate limit и таблица handshake ограничены по размеру и очищаются при timeout/disconnect. |
| NET-4 | UDP-транспорт поддерживает ровно одного remote peer; multi-peer функции заявляются только транспортом, который их реально реализует. |
| NET-5 | Reliable-очередь не создаёт «дыру»: при переполнении отбрасывается новый пакет, а не старый неподтверждённый. |
| NET-6 | Timeout очищает endpoint, peer id, временные буферы и pending handshake. |
| NET-7 | Повторный handshake от того же peer не создаёт второй peer и не сбрасывает активную сессию. |

## 7. UI и диагностика

| ID | Инвариант |
|---|---|
| UI-1 | UI не является источником истины: он отображает состояние и отправляет команды. |
| UI-2 | `GUI.color`, `contentColor`, `backgroundColor` восстанавливаются после отрисовки. |
| UI-3 | Окно и HUD не выходят за границы экрана; кнопка закрытия доступна. |
| UI-4 | 1×1 текстуры используют `border = 0`; 9-slice требует размеров больше border. |
| UI-5 | Шрифт имеет fallback, если выбранный системный шрифт недоступен. |
| UI-6 | Пользовательские строки не интерпретируются как rich text без экранирования. |
| UI-7 | Диагностика не раскрывает IP/Steam ID/пути без явного действия пользователя. |

## 8. Проверка перед релизом

Минимальный набор:

1. `dotnet test` — все тесты, 0 пропущенных.
2. Release и Debug — 0 ошибок и 0 предупреждений компилятора.
3. Реальный UDP loopback: handshake, все каналы, reconnect.
4. Ручной двухклиентный smoke: подключение, бой, смерть/revive, скамейка,
   переходы сцен, late join, quest-флаги.
5. Steam smoke с одинаковой версией у обоих игроков.

Автоматические тесты не заменяют пункты 4–5: они проверяют протокол, но не
поведение Unity-сцены и Steam API.
