# Анализ масштабирования на 3+ игроков

Дата: 2026-11-09. Протокол: **v8**. Документ не является обещанием поддержки
3+ в текущем релизе: он фиксирует, что уже готово, где остаются ограничения и
что потребуется для полноценного режима.

> **Исторический документ.** Написан для протокола v8. Текущий протокол — v11
> ([protocol-v11.md](protocol-v11.md)). Steam-транспорт с тех пор получил
> дополнительные peers (2–8, по умолчанию 2 игрока), поэтому часть выводов
> ниже уже реализована или устарела; ограничения UDP-транспорта остаются.

## Что уже поддерживает N игроков

| Компонент | Состояние |
|---|---|
| `PeerRegistry` | Реестр peer'ов с состояниями Connecting/Authenticated/Ready. |
| `CoopSessionState.RemotePeerIds` | Кэшированный список всех remote peer'ов. |
| `VitalsSyncService.RemotePeers` | Vitals хранятся per-peer. |
| `DeathLifecycleCoordinator` | Есть per-peer death/revive тесты. |
| `RemoteHornetSpawner` | Клоны хранятся в `Dictionary<NetworkPeerId, ...>`. |
| HUD напарников | Рисует блок для каждого peer'а из `VitalsSync.RemotePeers`. |
| `TransportBroadcast.SendToAll` | Рассылает пакет всем подключённым peer'ам. |
| Steam transport | Экспериментальный full-mesh: `SteamMaxPlayers` 2–8, дополнительные peer'ы и повышение primary. |
| Enemy authority | Хост остаётся единственным авторитетным симулятором; клиентские хиты откладываются при свежем host authority. |

## Ограничения

| ID | Ограничение | Влияние |
|---|---|---|
| N1 | `LiteNetLibTransport.MaxRemotePeers = 1` | UDP-сессия физически не может принять второго клиента. |
| N2 | `LiteNetLibTransport.SupportsHostRelay = false` | Нет UDP-relay для топологии host-and-spoke. |
| N3 | Handshake UDP не передаёт feature-set/роль | Хост не знает, поддерживает ли клиент multi-peer, и не может выбрать топологию. |
| N4 | `SilksongCoopPlugin` в ряде путей отправляет только `RemotePeerId` | Vitals/currency/bench/world-события могут не дойти до дополнительных peer'ов. |
| N5 | `ApplyRemoteHit` считает авторитетным только `RemotePeerId` | При смене primary или нескольких клиентах нужна явная роль хоста, а не «первый peer». |
| N6 | HUD не ограничен по высоте | 4–8 блоков могут выйти за экран. |
| N7 | Steam full-mesh не проверен живым тестом 3+ | Код есть, но нет подтверждённого сценария. |
| N8 | Reconnect/host migration не определены для 3+ | Уход хоста в full-mesh требует выбора нового авторитета или завершения сессии. |
| N9 | Квесты, инвентарь, сцена — двусторонние допущения | Нужен аудит каждого обработчика на «ровно один peer». |

## Что можно сделать без изменения протокола v8

1. **Steam experimental full-mesh**: довести до проверяемого состояния.
   - `ConnectedPeers` уже есть; заменить оставшиеся одиночные отправки на
     `SendToAll` там, где событие предназначено всем.
   - Явно определить primary peer как хоста, а не «первого подключённого».
   - Ограничить HUD по высоте и показывать счётчик скрытых peer'ов.
   - Добавить интеграционные тесты на 3 in-memory peer'а (Steam fake).
2. **Диагностика**: показывать количество peer'ов, роли и состояние каждого.
3. **UI**: status tab со списком peer'ов вместо одного партнёра.
4. **Тесты**: 3-peer сценарии для vitals, death, currency, world events,
   broadcast и reconnect на уровне сервисов.

Этого достаточно для **экспериментального Steam 3+** при явной настройке
`SteamMaxPlayers`, но не для стабильного релиза.

## Что требует нового протокола/архитектуры

1. **UDP host-relay**: хост принимает несколько клиентов и пересылает
   пакеты между ними. Нужны:
   - handshake с feature-set и ролью;
   - таблица peer endpoint'ов;
   - relay-правила и защита от петель;
   - лимиты полосы и backpressure на peer.
2. **Явный host identity**: поле/бит в handshake или отдельный control-пакет.
   Без него клиент не может отличить хоста от другого клиента после смены
   primary.
3. **Interest management**: не рассылать врагов/события peer'ам в других
   сценах; для 8 игроков это заметная экономия.
4. **Host migration**: либо запрещена и сессия завершается, либо новый хост
   выбирается детерминированно и получает полный state.
5. **Сохранения**: политика общего прогресса для 3+ (кто пишет в save,
   как обрабатываются конфликты).

Любое изменение wire-format означает новый `NetworkProtocol.Version` и
отдельную ветку. В v8 такие поля добавлять нельзя.

## Предлагаемый порядок

### Этап 1 — Steam experimental (без protocol bump)

- Аудит всех `RemotePeerId`-отправок, замена на broadcast там, где это
  семантически корректно.
- Явная проверка роли хоста в enemy authority.
- HUD: ограничение по высоте, список peer'ов.
- 3-peer fake-Steam тесты: broadcast, vitals, death, reconnect.
- Ручной smoke: 3 игрока в одном лобби, 30 минут.

**Критерий:** 3 игрока в Steam стабильны, 0 desync, host authority не
переключается на клиента.

### Этап 2 — UDP relay (protocol v9)

- Handshake feature-set + host role.
- Multi-endpoint таблица и relay.
- Relay-тесты: 3 и 4 клиента, потеря пакетов, reconnect.
- Ограничение полосы на peer.

**Критерий:** 4 игрока по UDP, 30 минут, 0 desync.

### Этап 3 — 8 игроков

- Interest management по сцене/дистанции.
- Батчинг snapshot'ов.
- HUD/UX для 8 игроков.
- Stress: 8 peer'ов, 1000 пакетов/с.

**Критерий:** 8 игроков — experimental, 4 — стабильно.

## Чего не делать

- Не включать `SteamMaxPlayers > 2` по умолчанию до прохождения этапа 1.
- Не добавлять поля в v8 «на всякий случай».
- Не обещать host migration до отдельного дизайна сохранений и авторитета.
- Не считать, что per-peer сервисы уже покрывают сцену/квесты: это нужно
  проверить отдельно.
