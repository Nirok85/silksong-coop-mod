# План улучшения качества и стабильности Silksong Co-op Mod

**Базовая версия:** v2.0.10 (commit `3286a10`, 623/623 тестов)
**Составлен:** после двух раундов глубокого аудита (BUG-01..BUG-20, BUG-A1..BUG-U2, BUG-N1..BUG-N16)
**Цель:** довести мод от «работающего прототипа» до production-grade: 0 варнингов, 0 known-issues, измеримая стабильность, воспроизводимые E2E-тесты, документированные ограничения.

---

## Принципы

1. **Тесты не модифицируются** (623 существующих должны проходить). Новые тесты — только добавлением файлов.
2. **Wire-формат не ломается** (PacketReader/Writer совместимость внутри v2.x).
3. **Каждый шаг — отдельный PR/коммит** с прохождением `dotnet test`.
4. **Mod-проект** компилируется только при наличии game DLL; изменения проверяются синтаксически (Roslyn) и логически по Core-тестам.
5. **Измеримость:** каждый шаг сопровождается метрикой (RTT, loss, GC alloc/frame, test count).

---

## Фаза 1 — Верификация и тестовая инфраструктура

### 1. CI-пайплайн (GitHub Actions)
- **Проблема:** нет автоматической проверки; регрессии ловятся вручную.
- **Действие:** workflow `build.yml`: push/PR → `dotnet build` Debug+Release с `TreatWarningsAsErrors=true`, запуск `dotnet test`, публикация артефактов (Core.dll, Mod.dll), кэш NuGet.
- **Принятие:** зелёный CI на каждый push; 0 errors / 0 warnings.
- **Риск:** Mod-проект требует game DLL → собирать только Core в CI (Mod — опционально с self-hosted runner).

### 2. Headless E2E-сценарии на MockNetworkTransport
- **Проблема:** тесты проверяют компоненты, но не полный путь «подключение → смерть → возрождение → синк».
- **Действие:** набор `E2E_*` тестов в Core, использующих `DualClientTestHarness` + `DeathLifecycleCoordinator` + `VitalsSyncService` + `InventorySyncService` на mock-транспорте: полный цикл смерти/вайпа, синк валюты при одновременных подборах, переподключение после drop 40% пакетов.
- **Принятие:** ≥ 10 новых E2E-тестов, все зелёные.

### 3. Тесты на property-based инварианты (FsCheck / самописные)
- **Проблема:** граничные значения (NaN, Infinity, отрицательные, wraparound) проверяются точечно.
- **Действие:** генераторы для `PacketValidator`, `RoomCodeCodec`, `SnapshotBuffer`, `HermiteSpline`, `SafeGroundSolver` с тысячами случайных входов.
- **Принятие:** 0 падений на 100k итерациях; найденные краевые случаи добавлены как регрессии.

### 4. Бенчмарки производительности (BenchmarkDotNet)
- **Проблема:** нет базовой линии для GC alloc/frame, времени сериализации, пропускной способности.
- **Действие:** проект `benchmarks/`, метрики: alloc на `BroadcastLocalTransform`, на пакет, на `PollEvents` при 1000 пакетах, память `SnapshotBuffer` при 60 FPS.
- **Принятие:** базовая линия зафиксирована в репо; регрессия > 20% блокирует PR.

## Фаза 2 — Сетевой слой

### 5. SACK (Selective Acknowledgment) для reliable-канала
- **Проблема:** текущий ACK подтверждает только один sequence; при потере ACK отправитель повторяет пакет, даже если получатель уже получил его.
- **Действие:** ACK-пакет несёт битовую маску последних 32 sequence; отправитель снимает с повторной отправки все подтверждённые.
- **Принятие:** при 10% loss повторные отправки снижаются ≥ 50%; тесты на mock-транспорте.
- **Риск:** изменение wire-формата ACK — нужна версия протокола (v3?) или опциональный флаг.

### 6. Адаптивный таймаут по RTT (вместо фиксированного 15 с)
- **Проблема:** heartbeat-timeout 15 с и connection-timeout 10 с не масштабируются с пингом; на WAN с RTT 300 мс ложные срабатывания, на LAN — медленное обнаружение.
- **Действие:** `timeout = max(base, rtt * k + jitter * 2)`; base 5 с, k = 4.
- **Принятие:** при RTT 200 мс таймаут ≈ 6 с; тесты с mock LatencyMs.

### 7. Fragmentation/Reassembly для пакетов > MTU
- **Проблема:** `LiteNetLibTransport` обрезает датаграммы > 2048 байт; `BroadcastInitialInventory` (512 байт) и большие сцены могут превышать MTU на некоторых каналах.
- **Действие:** флаг фрагментации в envelope (зарезервированный байт 7), сборка на приёмнике, таймаут 5 с на неполную сборку.
- **Принятие:** пакет 4 КБ доставляется целиком; тест на mock с фрагментами.

### 8. Многопировое расширение (опционально, Step 5 из improvement-plan)
- **Проблема:** архитектура однопировая; 3+ игроков невозможно.
- **Действие:** `Dictionary<NetworkPeerId, PeerState>` в транспорте; маршрутизация по отправителю; клон-менеджер на N.
- **Принятие:** 4-игровое лобби подключается, трансформы реплицируются всем.
- **Риск:** большой объём; отдельный этап (v3.0).

### 9. Безопасность: аутентификация direct-IP клиентов
- **Проблема:** direct-IP путь принимает клиентов без кода (BUG-B2 by design) — обход room-code защиты.
- **Действие:** опция `RequireRoomCode` (по умолчанию true для хостов с кодом); direct-IP клиенты отклоняются, если у хоста есть код. Документировать «LAN без кода» как явный режим.
- **Принятие:** тест: хост с кодом отклоняет handshake с флагом 0; хост без кода принимает.

## Фаза 3 — Игровая синхронизация

### 10. Единый источник истины для max-статов
- **Проблема:** `SharedMaxHealth` и т.п. обновляются в `VitalsSyncService`, применяются в плагине через events, но `PlayerData` может расходиться (например, после `MaxHealthKeepBlue`).
- **Действие:** применение max-статов только в одном месте (plugin event handler), с `RemoteApplyScope`, и немедленный `BroadcastCurrentVitals()` для повторного выравнивания.
- **Принятие:** тест: после upgrade у одного игрока оба имеют одинаковый `maxHealth`/`silkMax`/`nailUpgrades`.

### 11. Валюта: reconciliation по `TotalWalletAmount`
- **Проблема:** `HandleCurrencyPacket` игнорирует `TotalWalletAmount` при `delta != 0` — любой дрейф (lost packet, хотя reliable) остаётся.
- **Действие:** если `|SharedRosaries - TotalWalletAmount| > threshold` → принять `TotalWalletAmount` как авторитетный (с логом). Добавить `OnSharedCurrencyReconciled` event.
- **Принятие:** тест: инъекция расхождения → схождение за один пакет.

### 12. Смерть/возрождение: state-machine с явными переходами
- **Проблема:** `DeathLifecycleCoordinator` имеет неявные переходы (например, `RespawningAtPartner` без таймаута; `OnLocalPlayerDied` при `CurrentState == Spectating`).
- **Действие:** явная таблица переходов, валидация в `HandleDeathPacket`, логирование невалидных, unit-тесты на каждый переход.
- **Принятие:** 100% покрытие переходов тестами; 0 невалидных переходов в логах при E2E.

### 13. Клон: scene-aware видимость и буфер
- **Проблема:** при смене сцены буфер снапшотов очищается, но `_clockOffsetMs` сохраняется; при возврате в сцену клон может «прыгнуть».
- **Действие:** сброс `_clockOffsetMs` при смене сцены (уже частично), плюс snap-to-partner при первом пакете в новой сцене.
- **Принятие:** E2E-тест: переход сцены → возврат → клон появляется без «телепорта».

## Фаза 4 — Производительность и GC

### 14. Устранить оставшиеся аллокации в горячем пути
- **Проблема:** `DashTrailController.EmitGhostAfterImage` создаёт `new GameObject` при пустом пуле (до 20); `PaletteSwapController.ApplyPaletteSwap` вызывает `ren.materials` (массив) раз в 30 кадров.
- **Действие:** pre-warm пул при инициализации; кэшировать `materials` массив; замерить alloc/frame до/после BenchmarkDotNet.
- **Принятие:** ≤ 0 alloc/frame на горячем пути трансформа; ≤ 1 KB/frame в бою.
- **Связано:** BUG-P1/P2/P3 уже частично сделаны.

### 15. Кэширование reflection в KeybindManager
- **Проблема:** `CheckNewInputSystemKey` вызывает `Type.GetType` и `GetProperty` каждый кадр, если legacy-ввод недоступен.
- **Действие:** кэшировать `Type`/`PropertyInfo` в статические поля при первом вызове.
- **Принятие:** 0 reflection-вызовов после инициализации; профайлер подтверждает.

### 16. Пул объектов для пакетов (ArrayPool<byte>)
- **Проблема:** каждый `Send` аллоцирует `new byte[length]` (трансформ 30 раз/с).
- **Действие:** использовать `ArrayPool<byte>.Shared.Rent/Return`; envelope-буферы возвращаются после `SendTo`.
- **Принятие:** 0 alloc на отправку трансформа; тесты на корректность возврата.

## Фаза 5 — Архитектура и поддерживаемость

### 17. Декомпозиция `SilksongCoopPlugin` (1649 строк)
- **Проблема:** god-object смешивает оркестрацию транспорта, event-wiring, revive, item-apply, transform-broadcast, lifecycle.
- **Действие (по improvement-plan Step 1):**
  - `NetworkOrchestrator` (выбор транспорта, connect/disconnect, polling)
  - `GameplaySyncController` (revive, team wipe, item apply, vitals apply)
  - `TransformReplicationService` (tick-based broadcast)
  - `SilksongCoopPlugin` — тонкая точка входа BepInEx, которая связывает сервисы
- **Принятие:** каждый сервис < 300 строк; плагин < 200 строк; все тесты проходят; поведение идентично.
- **Риск:** большой рефакторинг без compile-проверки Mod — делать инкрементально, по одному сервису за PR.

### 18. Устранение nullable-предупреждений (CS8602) в Mod
- **Проблема:** 30 предупреждений в `CoopMenuUI.cs` и других Mod-файлах.
- **Действие:** null-гарды, `?.`, аннотации `[NotNull]`, включение `TreatWarningsAsErrors` в CI для Core (Mod — опционально).
- **Принятие:** 0 warnings в Debug+Release.

### 19. Документирование ограничений и failure-modes
- **Проблема:** README описывает фичи, но не failure-modes (что происходит при разрыве, при рассинхроне, при моде на одной стороне).
- **Действие:** раздел «Известные ограничения» в README (RU+EN): 2 игрока, одинаковая версия игры/мода, Steam-overlay для интернета, нет shared simulation врагов, max-health только растёт.
- **Принятие:** документ принят; FAQ дополнен.

### 20. Версионирование протокола и backward-compat
- **Проблема:** нет номера протокола; при добавлении полей старые клиенты ломаются.
- **Действие:** `ProtocolVersion` в `PacketHeader` (зарезервированный байт 7), проверка при handshake, graceful disconnect с `DisconnectReason.VersionMismatch`.
- **Принятие:** клиент со старой версией получает понятное сообщение; тест на mock.

## Приоритизация (рекомендуемый порядок)

1. **Фаза 1 (1–4)** — инфраструктура, чтобы дальше было безопасно менять.
2. **Фаза 2 (5–7)** — надёжность сети (SACK, адаптивный таймаут, фрагментация).
3. **Фаза 3 (10–13)** — корректность синхронизации (max-статы, валюта, смерть, сцены).
4. **Фаза 4 (14–16)** — производительность.
5. **Фаза 5 (17–20)** — архитектура и документация.
6. **Фаза 2 (8–9)** — multi-peer и безопасность direct-IP — отдельный этап (v3.0), требует обсуждения.
