## LOCAL_FIX — bounded tasks for Qwen2.5-Coder 7B

### L1 — Medium: release tags do not require Mod verification when runner is disabled

Location: `.github/workflows/ci.yml:149,204-226`.

`mod` is skipped when `SILKSONG_MOD_RUNNER_ENABLED` is not true. `REQUIRE_MOD` only becomes true for a release tag when that same variable is true. Therefore a `v*` tag with the runner disabled passes the status gate without compiling Mod. This is an automation coverage gap, not evidence that the present local build fails.

Fix scope: make release-tag verification required independently of runner availability; a disabled runner must fail a tagged release explicitly, or introduce an explicit documented separate policy for unverified tags. Do not broaden runner access to untrusted PRs.

Acceptance: exercise tag/branch/dispatch cases with runner enabled and disabled; tag + disabled runner must not report successful required Mod coverage.

Evidence: direct Boolean evaluation of workflow expressions; GitHub Actions was not executed remotely.

### L2 — Medium: wallet-seed retry allowance depends on rendering/pump frequency

Location: `src/SilksongCoop.Mod/SilksongCoopPlugin.cs:112,1597-1598,1714-1755`.

`WalletSeedMaxAttempts = 240`; every unsuccessful `PumpWalletSeed` decrements the allowance, with no next-attempt timestamp. The pump is invoked from readiness processing, including incoming packet handling. A refusal lasting the same real duration can disconnect at high FPS but survive at low FPS. 240 pump calls are about one second at 240 calls/second, not a network timeout; incoming traffic can consume the budget faster still. This affects the refusal path, not normal accepted/queued sends.

Fix scope: monotonic real-time deadline and throttled retry interval; retain already captured chunk state and existing bounded fail-closed behavior.

Acceptance: a new test drives the same refusal interval at 30/60/240 pump calls per second and verifies the same timeout behavior; accepted retry removes the outstanding peer exactly once.

Evidence: static control-flow confirmation; no real Steam backpressure run.

## COMPLEX_FIX — cross-component work, not a blind 7B patch

### C1 — High: reconnect can resume an incomplete initial wallet-seed exchange

Locations: `src/SilksongCoop.Mod/SilksongCoopPlugin.cs:1426-1429,1553-1565,1579-1591,1627-1663,1954-1959`.

Mechanism:
1. First connection records peer save identities in `_walletPeerInstances`; client begins collecting a seed.
2. Disconnect occurs before the first seed is completely applied.
3. Readiness reset clears `_awaitingWalletSeed` and assembler, but preserves wallet-save/room and peer identities for resume.
4. Reconnect to the same room with the same PlayerData makes `resume` true; the same PeerReady token makes `resumedPeer` true.
5. Host skips seed delivery; client skips the branch that sets `_awaitingWalletSeed`. Currency traffic can resume although authoritative initial balance was never established. An unfinished seed-collection state may also remain until its transaction buffer exhausts.

Fix direction: track completed seed establishment separately from identity continuity. Resume only after a completed bootstrap; otherwise authorize a fresh exchange, reset assembler/collection consistently and preserve unconfirmed local deltas without replaying already included transactions.

Acceptance: drop connection before chunk zero, between chunks and after application; reconnect to same room/save and prove equal balances and exactly-once deltas. Cover both peers knowing the other's save identity before disconnection.

Evidence: traced current state transitions; requires production integration reproduction. Do not call this dynamically reproduced.

### C2 — High: abandoned pending counter application blocks later events after a 3+ reconnect

Locations: `src/SilksongCoop.Core/State/InventorySyncService.cs:289-290,334-350,393-399`; `src/SilksongCoop.Mod/SilksongCoopPlugin.InventoryRetry.cs:35-40`; `src/SilksongCoop.Mod/SilksongCoopPlugin.cs:1387-1402,1642-1645`.

A failed counter apply records `(sequence, transaction)` for its sender. Other events from that sender return false until the exact pending event succeeds. When an additional peer disconnects and the session continues, the retry pump discards its queue entry because the peer is absent, but the Core pending marker is not cleared. Reconnect using the same save identity does not call `ResetCounterPeer`. A new baseline has a different transaction, cannot pass the pending guard and eventually reaches the inventory retry timeout/disconnect. Keeping sequence replay protection is correct; leaving an unserviceable pending marker is not.

Dynamic Core reproduction, outside the repository: first counter apply returns false; applier becomes healthy; a new counter from the same peer still returns false; after explicit peer reset it returns true. The full 3+ Unity reconnect scenario was not run.

Fix direction: define ownership of pending work across disconnects. Retain/retry the exact pending event or cancel pending application while preserving the committed sequence watermark. Do not simply clear all replay history on ordinary reconnect.

Acceptance: additional peer disconnects during failed fragment apply while two peers remain; reconnect same save; new baseline and subsequent deltas complete exactly once without a forced session reset.

### C3 — High verification gap: E2E helpers can pass without exercising production Mod behavior

### C4 — Medium: refused currency receipts have no in-session retry path

Locations: `src/SilksongCoop.Mod/SilksongCoopPlugin.cs:1933-1948`; `src/SilksongCoop.Mod/Services/VitalsSyncManager.cs:174-186,218-234`.

After applying a currency packet, the receiver sends a receipt once; a false send result only logs. The sender adds an accepted transaction to `_currencySent`, then skips it on every later journal flush. There is no application-level timeout removing that sent marker or requesting another receipt. If the transport refuses a receipt without immediately ending the session, the unconfirmed journal entry cannot recover until reconnect and can contribute to journal exhaustion. Current transport overflow often disconnects, limiting practical exposure; the precise transient-refusal scenario was not exercised against Steam.

Fix direction: bounded receipt retry or timed idempotent replay of unconfirmed currency transactions; coordinate application replay watermarks, seed inclusion and reconnect journals. Avoid unbounded acknowledgement queues and avoid resending the entire journal every frame.

Acceptance: transport accepts transaction, refuses exactly its first receipt, then becomes healthy; both wallets apply once and the sender journal eventually empties without reconnect.

Evidence: static trace; conditional on a nonfatal send refusal. Not a claim of ordinary UDP packet-loss failure: reliable transport retransmission already handles network loss after acceptance.
